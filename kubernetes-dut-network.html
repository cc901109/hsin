CASE STUDY 01 · SYSTEMS / NETWORKING

Kubernetes ×
Physical DUT Network

當原本建立於單機 Docker 環境的產品測試流程遷移至 Kubernetes，Test Pod 除了需要保留 Kubernetes 原有的 Pod Network，也必須能夠連接實體 DUT 測試網路， 並從 DUT-side DHCP 取得測試所需的網路位址。

ROLE Architecture / PoC / Integration
STACK Kubernetes / Multus / macvlan
FOCUS Multi-Network Integration
01 / CONTEXT

從單機 Container Network， 到 Kubernetes Multi-Network。

原有測試環境以單機 Docker 為基礎， Container 可以透過 Host 上既有的測試網路， 與實體產品（DUT）進行連線。

當測試服務逐步移往 Kubernetes 後， 網路模型產生了根本性的差異。 Pod 預設透過 Kubernetes CNI 加入 Cluster Pod Network， 但產品測試所需要的網路並不是單純的 Cluster 內部通訊， 而是必須進一步連接至實體 DUT 所在的測試網路。

ENGINEERING QUESTION

如何在保留 Kubernetes 預設 Pod Network 的同時， 為 Test Pod 增加另一個可直接進入 Physical DUT Network 的網路介面？

02 / CONSTRAINTS

問題不只是「讓 Pod 能上網」。

這個需求的核心並非一般 Kubernetes Service-to-Service 通訊，而是 Container、Host Network 與實體測試設備之間的整合。 因此設計時需要先拆開不同的網路邊界。

01

保留 Pod Network

Test Pod 仍需要 Kubernetes 預設網路， 用於平台內部服務與 Cluster 通訊。

02

第二張 Network Interface

測試流量需要走獨立介面， 不能單純以預設 Pod Interface 取代。

03

Physical DUT Network

Container 必須實際進入與 DUT 相連的實體測試網路， 而非只存在於 Kubernetes Overlay Network。

04

DUT-side DHCP

額外的測試介面需要透過 DUT-side DHCP 取得對應測試網段的 IP。

03 / ANALYSIS

先確認系統邊界，再選擇技術。

面對這個問題時，我先釐清 Kubernetes 預設 CNI、 Node Physical NIC、Container Interface 與 DUT Network 各自負責的範圍，再調研 Kubernetes Multi-Network 相關方案。

核心需求是讓一個 Pod 同時存在於兩個不同的網路環境： 一個維持 Kubernetes 原本的 Pod Network， 另一個則專門承載實體產品測試流量。

04 / ARCHITECTURE

Multus CNI 作為 Multi-Network 的入口。

最終架構採用 Multus CNI， 讓 Test Pod 在 Kubernetes 預設網路之外， 依據 NetworkAttachmentDefinition 建立額外的網路介面。

WORKLOAD Test Pod Default Interface + Secondary Interface
↓
MULTI-NETWORK Multus CNI Attach additional network
↓
CONFIGURATION NetworkAttachmentDefinition Define secondary network
↓
NETWORK macvlan + DHCP Secondary interface & IP assignment
↓
PHYSICAL TEST NETWORK DUT Network Product-side test environment
Kubernetes Pod → Multus CNI → NAD → macvlan → DHCP → DUT Network
05 / IMPLEMENTATION

把 Kubernetes Network Model 對接既有測試需求。

Multus 負責讓 Pod 能夠附加額外的 Network， NetworkAttachmentDefinition 則描述該網路的設定。 Secondary Network 使用 macvlan， 讓 Container 的額外介面能夠進入實體測試網路。

IP 配置則配合 DUT-side DHCP， 使 Test Pod 的測試介面能依照實際產品測試環境取得位址， 而 Kubernetes 原有的 Default Interface 仍維持原本 Cluster Network 的功能。

06 / VALIDATION

驗證重點是整條資料路徑， 而不是單一元件是否啟動。

PoC 與整合過程中，驗證的重點包含 Pod 是否成功取得 Secondary Interface、是否能透過 DUT-side DHCP 取得測試網段 IP，以及 Container 到 Physical DUT Network 的連線是否符合測試需求。

✓

07 / TAKEAWAY

從「網路設定問題」， 轉化成「系統架構問題」。

這個案例讓我更清楚理解， Container Networking 並不是獨立存在的設定項目。 當 Kubernetes 與實體測試設備整合時， CNI、Linux Networking、Physical NIC、 DHCP 與 DUT Network 都會共同影響最終行為。

相較於直接尋找單一指令或設定， 我更傾向先建立系統模型、確認各層責任與資料路徑， 再透過 Survey、PoC 與逐層驗證縮小問題範圍。 這也成為我後續處理平台、網路與效能問題時的重要方法。
